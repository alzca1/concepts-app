= Data model and persistence

A card is a row in the `public.concepts` table of the managed
Postgres database (Supabase):

[source,sql]
----
create table public.concepts (
  id         uuid        primary key default gen_random_uuid(),
  user_id    uuid        references auth.users(id) on delete cascade not null,
  front      text        not null,
  back       text        not null,
  tag        text        not null default '',
  created_at timestamptz not null default now(),
  updated_at timestamptz not null default now()
);
----

The TypeScript domain type mirrors the row minus the server-only
columns:

[source,ts]
----
interface Concept {
  id: string;
  front: string;
  back: string;
  tag: string;
  createdAt: number;  // ms epoch parsed from created_at
}
----

== Invariants

* `id` is a UUID generated by Postgres (`gen_random_uuid()`).
* `user_id` is the signed-in user's id, populated server-side by the
  repository before insert; the client never sets it.
* `created_at` is set by Postgres on insert and preserved on update;
  the trigger `concepts_set_updated_at` keeps `updated_at` current.
* Row-Level Security is the only access path: the policy
  `Users manage own concepts` filters every `SELECT`/`INSERT`/
  `UPDATE`/`DELETE` by `auth.uid() = user_id`. The client cannot
  bypass it, even with a forged JWT, because the policy runs in the
  database, not in the application.

== Persistence layer

`application/api/concepts-repository.ts` is the only module that
touches Supabase:

* `listConcepts()` — returns the current user's cards, newest first.
* `createConcept(input)` — inserts a card owned by `auth.uid()`.
* `updateConcept(id, input)` — updates an owned card.
* `deleteConcept(id)` — deletes an owned card.

The store (`application/store/use-concepts/`) owns the React state,
loads on session change and reflects each mutation back into the
list. UI components never touch the repository directly — they
receive data and callbacks from the hook.

== Migrations

A schema change to `public.concepts` is a hard cut-over (no
`localStorage`-style versioning on the server): ship the migration
SQL, deploy, and ensure the application reads the new shape before
the database has any rows in the old shape.
